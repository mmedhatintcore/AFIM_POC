# Internationalization (i18n)

**Languages**: Arabic (`ar`) — default for KSA market — and English (`en`). Full **RTL** support from Day 1, not retrofitted.

Library: **`next-intl`** (App Router–native, works in RSC and client components).

---

## URL Strategy

Every route is prefixed with the locale:

```
/ar/events/luna-park
/en/events/luna-park
/ar/dashboard/bookings
/en/dashboard/bookings
```

- `middleware.ts` matches unprefixed URLs (`/events`) and rewrites to the default locale (`/ar/events`) or honors `Accept-Language`.
- Locale segment is `[locale]` and lives at the top of `src/app/`.
- Never hard-code `/events/...` in `<Link>` — always `{ href: '/events', locale }`.

---

## Folder Layout

```
src/
  app/
    [locale]/
      layout.tsx           # sets <html lang dir>, loads fonts, wraps NextIntlClientProvider
      page.tsx
      events/
        page.tsx
  messages/
    en.json                # flat or nested namespaces
    ar.json                # parallel to en.json — every key must exist in both
  i18n/
    routing.ts             # defineRouting() — locales, defaultLocale, pathnames
    request.ts             # getRequestConfig() — pulls messages by locale
```

## Root Layout — dir + lang

```tsx
// app/[locale]/layout.tsx
import { NextIntlClientProvider } from 'next-intl';
import { getMessages } from 'next-intl/server';
import { notFound } from 'next/navigation';
import { routing } from '@/i18n/routing';

export default async function LocaleLayout({
  children,
  params,
}: {
  children: React.ReactNode;
  params: Promise<{ locale: string }>;
}) {
  const { locale } = await params;
  if (!routing.locales.includes(locale as any)) notFound();

  const messages = await getMessages();
  const dir = locale === 'ar' ? 'rtl' : 'ltr';

  return (
    <html lang={locale} dir={dir}>
      <body>
        <NextIntlClientProvider messages={messages} locale={locale}>
          {children}
        </NextIntlClientProvider>
      </body>
    </html>
  );
}
```

The `dir="rtl|ltr"` on `<html>` is what makes Tailwind logical utilities (`ps-*`, `me-*`) flip automatically. **Never** set `dir` on a nested element unless you genuinely need mixed direction.

## No Inline Translations — Hard Rule

**Every user-facing string must come from `messages/{en,ar}.json`.** No exceptions for "just this one short label" or "it's only two words." Inline ternaries on `locale` scatter translations across the codebase, bypass translator tooling, make string audits impossible, and guarantee one locale will drift out of sync with the other.

### ❌ Wrong

```tsx
// Any of these is a bug, regardless of string length:
const title = locale === 'ar' ? 'الفعاليات' : 'Events';

<h1>{locale === 'ar' ? 'احجز الآن' : 'Book now'}</h1>

const label = isArabic ? 'حفظ' : 'Save';

// Also wrong — hard-coded English fallback:
<button>{t('save') ?? 'Save'}</button>

// Also wrong — concatenating translated fragments:
<p>{t('hello')}, {user.name}!</p>  // use ICU: t('hello', { name: user.name })
```

### ✅ Right

```tsx
// Server component
import { getTranslations } from 'next-intl/server';
const t = await getTranslations('Events');
<h1>{t('title')}</h1>

// Client component
'use client';
import { useTranslations } from 'next-intl';
const t = useTranslations('Events');
<button>{t('bookNow')}</button>
```

With the corresponding entry in **both** message files:

```json
// messages/en.json
{ "Events": { "title": "Events", "bookNow": "Book now" } }

// messages/ar.json
{ "Events": { "title": "الفعاليات", "bookNow": "احجز الآن" } }
```

### The only exceptions

These genuinely should not be translated — keep them as literals (see also the "What NOT to Translate" section):

- API payload values (`status: 'draft'`, `payment_method: 'mada'`)
- Slugs, codes, SKUs, identifiers
- Brand name "Sight Scape"
- Debug-only strings behind `process.env.NODE_ENV !== 'production'`

For **everything else visible to a user** — button labels, empty states, aria-labels, placeholder text, toast messages, error copy, tooltip text, loading skeleton text — the key lives in the JSON file.

### Catching violations

- A grep/lint rule on `locale === 'ar'` / `locale === 'en'` in `src/components/` and `src/app/` catches ternary-translation attempts.
- PRs that introduce a new user-visible string without a matching `en.json` + `ar.json` entry should fail review.
- Run the app with `Accept-Language: ar` on every new page before merging — any residual English literal shows up immediately.

## Translation Files

Use namespaced JSON:

```json
// messages/en.json
{
  "Common": {
    "save": "Save",
    "cancel": "Cancel",
    "loading": "Loading…"
  },
  "Events": {
    "title": "Events",
    "filter.featured": "Featured",
    "empty": "No events match your filters."
  }
}
```

```json
// messages/ar.json
{
  "Common": {
    "save": "حفظ",
    "cancel": "إلغاء",
    "loading": "جارٍ التحميل…"
  },
  "Events": {
    "title": "الفعاليات",
    "filter.featured": "المميزة",
    "empty": "لا توجد فعاليات تطابق الفلاتر."
  }
}
```

**Rules:**
- Every key in `en.json` must exist in `ar.json`, and vice versa. Lint this in CI.
- Group by feature / page. Avoid a monolithic `common` bucket.
- Never concatenate translated strings (`t('hello') + ', ' + name`) — use ICU placeholders (`"greeting": "Hello, {name}"`).

## Using Translations

### Server components

### Client components

```tsx
'use client';
import { useTranslations } from 'next-intl';

export function FilterChip({ active }: { active: boolean }) {
  const t = useTranslations('Events');
  return <button>{t('filter.featured')}</button>;
}
```

### Plurals and interpolation (ICU)

```json
"bookings.count": "{count, plural, =0 {No bookings} one {# booking} other {# bookings}}"
```

```tsx
{t('bookings.count', { count: bookings.length })}
```

Arabic has **six** plural forms (`zero`, `one`, `two`, `few`, `many`, `other`) — ICU handles them correctly when you provide all the branches.

## Date & Time Formatting

Never format dates with ad-hoc string concatenation. Use `next-intl` formatters, which wrap `Intl.DateTimeFormat`:

```tsx
import { useFormatter } from 'next-intl';

const format = useFormatter();
format.dateTime(event.startsAt, { dateStyle: 'long', timeStyle: 'short' });
```

For Arabic, the same call returns Arabic-Indic numerals and localized month names. The backend always sends **ISO 8601** — parse with `new Date(iso)`.

The platform uses the **Gregorian calendar only**. Do not introduce Hijri (Islamic) date display — it is explicitly out of scope.

## Timezones

**Saudi-operated platform, global customers.** A traveler in London books a Saudi experience for next month. The experience happens in `Asia/Riyadh` (UTC+3, no DST); the customer reads about it in `Europe/London` (UTC+0/+1 with DST). Both timezones matter.

**Canonical rules** (mirrored on the backend in `backend/.claude/rules/api-conventions.md`):

1. **Backend sends UTC ISO 8601 strings.** `2026-05-14T15:00:00Z`. Always.
2. **Detect the user's timezone in the browser** with `Intl.DateTimeFormat().resolvedOptions().timeZone` — yields IANA names like `Europe/London`, `Asia/Riyadh`, `America/New_York`.
3. **Send the timezone on every API request** via the `X-Timezone` header (axios interceptor, alongside `Accept-Language`). The backend uses it for transactional emails / WhatsApp messages and persists it on `users.timezone` so server-rendered emails sent later (e.g. booking reminders) get the right zone too.
4. **Two ways to render a backend timestamp:**
   - **The experience's local time (Riyadh):** `format.dateTime(date, { ..., timeZone: 'Asia/Riyadh' })`. Use for the *primary* display of when an experience starts — this is when it actually happens, regardless of where the user is.
   - **The user's local time:** `format.dateTime(date, { ..., timeZone })` where `timeZone` is the browser-detected value. Use as a *secondary* line beside the Riyadh time so travelers can plan around their flight.
5. **Always label which zone is shown** when ambiguity matters: "**3:00 PM Riyadh time** (12:00 PM in your time zone)". Never display a bare "3:00 PM" for a date that's not "today" — readers assume their own zone.
6. **Countdowns and durations** ("expires in 5 minutes", the OTP resend `0:40`) are timezone-agnostic — they're relative wall-clock seconds, JS `setInterval` based. No special handling required.
7. **Don't trust the browser's clock for security.** Token / OTP expiry is enforced server-side against UTC; the client just shows a human-friendly countdown.
8. **Saudi-only displays** — admin dashboards, receipts, invoices, ops UIs — pin to `Asia/Riyadh` regardless of the viewing user's timezone. ZATCA-format invoices must always render Riyadh time (legal requirement).
9. **`useFormatter` accepts `timeZone`** — pass it explicitly. Without it, `Intl` defaults to the browser zone, which is correct for *user-personal* views but wrong for *experience-in-Saudi* views.
10. **Numerals stay Latin** even when formatting in Arabic — pass `numberingSystem: 'latn'` (see "Numerals" section above).

**Quick decision flow:**
- "When does this thing happen?" (event start, slot time) → render in `Asia/Riyadh`, optionally annotate with user-zone secondary
- "When did the user do something?" (booking placed, account created) → render in user's browser timezone
- "Internal admin / accounting / legal" → render in `Asia/Riyadh`, always
- "Countdowns" → no timezone, just `setInterval`

## Money Formatting

Backend returns integer **halalas**. Format at the presentation boundary:

```ts
// lib/utils/money.ts
export function formatSAR(halalas: number, locale: 'en' | 'ar'): string {
  return new Intl.NumberFormat(locale === 'ar' ? 'ar-SA' : 'en-SA', {
    style: 'currency',
    currency: 'SAR',
    currencyDisplay: 'symbol',
  }).format(halalas / 100);
}
```

- `ar-SA` → `١٥٠٫٠٠ ر.س.`
- `en-SA` → `SAR 150.00`

Never hand-concatenate the currency label — let `Intl` place it (Arabic renders it on the other side).

## Numerals — always Latin (Western)

**Project-wide policy: numbers always render in Latin numerals (`123`), never Arabic-Indic (`١٢٣`), regardless of locale.** This is a deliberate product decision — do not flip it without explicit approval.

`Intl` defaults to Arabic-Indic in `ar-SA`, so every formatter must explicitly pass `numberingSystem: 'latn'`:

```ts
// ✅ correct
new Intl.NumberFormat('ar-SA', {
  style: 'currency',
  currency: 'SAR',
  numberingSystem: 'latn',
}).format(1234);
// → "ر.س.‏ 1,234.00"

// ❌ wrong — produces ١٬٢٣٤٫٠٠
new Intl.NumberFormat('ar-SA', { style: 'currency', currency: 'SAR' }).format(1234);
```

Apply equally to:

- `Intl.NumberFormat` — prices, counts, percentages, decimals.
- `Intl.DateTimeFormat` — pass `numberingSystem: 'latn'` so dates render `٢٠٢٦-٠٤-٢٥` → `2026-04-25`.
- `useFormatter().dateTime(...)` / `.number(...)` from next-intl — these accept the same option.
- Any custom number-rendering utility — propagate `numberingSystem: 'latn'` end-to-end.

The shared utilities in `lib/utils/money.ts` (`formatSAR`, `formatSARAmount`) and the per-component formatters (e.g. `formatPrice` in `hero-card.tsx`) already enforce this. Reuse them; don't roll new formatters that drop the option.

> Out of scope: if a future flow truly needs Arabic-Indic digits (e.g. matching a third-party PDF/receipt), call it out in the PR description and approve explicitly. The default is Latin.

## Locale Switcher

```tsx
'use client';
import { useRouter, usePathname } from '@/i18n/routing';
import { useLocale } from 'next-intl';

export function LocaleSwitcher() {
  const locale = useLocale();
  const router = useRouter();
  const pathname = usePathname();
  const next = locale === 'ar' ? 'en' : 'ar';

  return (
    <button onClick={() => router.replace(pathname, { locale: next })}>
      {next === 'ar' ? 'العربية' : 'English'}
    </button>
  );
}
```

Store the last chosen locale in a **cookie** (`ts.locale`) so SSR and the axios instances (see [api-client.md](./api-client.md)) agree on language without a round trip.

## Accept-Language Header

Every axios request sends `Accept-Language: ar` or `en` (see [api-client.md](./api-client.md)). The backend uses this to return translated error messages and `messages.*` keys — we do **not** translate backend error messages on the client.

## RTL UI Checklist

When building a new screen, verify in Arabic:

- [ ] `<html dir="rtl">` active — read direction flipped.
- [ ] Icons with direction (arrows, chevrons) mirrored via `rtl:rotate-180` or direction-aware component.
- [ ] No `ml-*` / `mr-*` / `left-*` / `right-*` (use `ms-*` / `me-*` / `start-*` / `end-*`).
- [ ] Text alignment uses `text-start` / `text-end`, not `text-left` / `text-right`.
- [ ] Form fields, tables, carousels work right-to-left without overflow.
- [ ] Currency symbol and numerals render correctly.
- [ ] Page works at RTL line-lengths — Arabic is ~20% longer on average than English.

Test both locales at every PR. A "works in English" PR that breaks Arabic is a regression.

## SEO — Localized Metadata & hreflang

Every public page must declare both locales via `hreflang` alternates so Google and Bing serve the right version in the right market, and so Arabic / English variants don't cannibalize each other.

### `hreflang` in `generateMetadata`

```tsx
export async function generateMetadata({ params }): Promise<Metadata> {
  const { locale, slug } = await params;
  const base = process.env.NEXT_PUBLIC_SITE_URL;

  return {
    alternates: {
      canonical: `${base}/${locale}/events/${slug}`,
      languages: {
        en: `${base}/en/events/${slug}`,
        ar: `${base}/ar/events/${slug}`,
        'x-default': `${base}/en/events/${slug}`,
      },
    },
    openGraph: { locale: locale === 'ar' ? 'ar_SA' : 'en_US' },
  };
}
```

`x-default` points to the fallback when Google can't match a user's locale — use English.

### Localized titles, descriptions, OG text

Titles and descriptions are **translated**, not transliterated. Load them from the message bundle or directly from the backend (for dynamic entities like event titles):

```tsx
const t = await getTranslations({ locale, namespace: 'Events' });
return { title: t('meta.title'), description: t('meta.description') };
```

For dynamic content (event title, venue name) use the backend-returned translation — `getTranslation('title', locale)` on the backend returns the right string based on `Accept-Language`.

### Sitemap — emit both locales

`src/app/sitemap.ts` emits every public URL in both locales with cross-referenced `alternates`:

```ts
import type { MetadataRoute } from 'next';

export default async function sitemap(): Promise<MetadataRoute.Sitemap> {
  const events = await fetchPublishedEvents();
  const base = process.env.NEXT_PUBLIC_SITE_URL!;

  return events.flatMap((e) => ['en', 'ar'].map((locale) => ({
    url: `${base}/${locale}/events/${e.slug}`,
    lastModified: e.updated_at,
    changeFrequency: 'daily' as const,
    priority: 0.8,
    alternates: {
      languages: {
        en: `${base}/en/events/${e.slug}`,
        ar: `${base}/ar/events/${e.slug}`,
      },
    },
  })));
}
```

### Content authoring rules for SEO

- **No identical titles across locales.** A page titled "Events" in both English and Arabic (`Events` vs `الفعاليات`) is fine; a page titled `"Events"` in both is a bug.
- **Slugs stay ASCII** (`luna-park`) — the same slug works for both locales. Don't create `/ar/الفعاليات/...` URLs; Latin slugs are more shareable, more analytics-friendly, and easier to type on a non-Arabic keyboard.
- **Meta description target**: 120–160 characters **per locale**. Arabic runs longer per character visually but similar in meta-length budget.
- **Title tag target**: ≤ 60 characters per locale.

See the cross-cutting SEO/SSR rules in [architecture.md](./architecture.md).

## What NOT to Translate

- Identifiers / slugs / codes (`ABC-123`, `event-slug`).
- Email, phone, IBAN, SKU.
- Brand name "Sight Scape" — keep as-is unless the brand guide provides an Arabic logotype.
- Enum values sent to the API (`status: "draft"`, `payment_method: "mada"`).

The backend stores these as plain columns (see `backend/.claude/rules/spatie-translatable.md`) — the frontend must send them in exactly the canonical form.
